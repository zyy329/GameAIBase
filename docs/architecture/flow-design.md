# 我的需求：AI 项目经理系统（最终综合版）

## 一、系统定位

构建一个 **AI 项目经理系统**，核心职责是：

- 管理项目全生命周期的推进
- 维护任务与创意的双轨流转
- 支持在新会话时提供进度摘要和下一步建议
- 与 执行管线（如 CCGS、GameDesignOS，GDD 等）协作：AI 项目经理管"做什么、做到哪了"，执行管线 管"怎么做"
- 支持手动触发和自动维护两种形式：
  - 手动触发：用户通过斜杠命令或自然语言触发
    - 任务轨道
      - 创建/更新/状态变更
      - 会话恢复（新开会话后，AI会话能识别出当前项目进展到哪里了，下一步该干什么） -- 非自动
    - 创意轨道的
      - 创建/更新创意
      - 创意升格到任务轨道
  - 自动维护：
    - 任务轨道
      - 自动更新任务状态
      - 状态收敛
      - UID生成，SEQ变更维护

---

## 二、核心机制：需求管道（Demand Pipeline）

需求管道是顶层概念，包含两条并行轨道：

### 轨道一：任务轨道（Task Track）

- **定位**：已进入计划、待执行的任务及其状态维护
- **核心职责**：
  - 接收来自逐层拆解的主路径任务
  - 接收来自创意轨道升格的支流任务
  - 维护任务状态流转与进度追踪
  - 支持按需读取，避免 AI 一次性加载过多内容

### 轨道二：创意轨道（Idea Track）

- **定位**：暂存、待评估的点子
- **核心职责**：
  - 收集用户随时提出的新想法或其他零散未整理计划
  - 暂存待评估，不直接进入执行计划
  - 经评估确认后升格/拆分为任务，汇入任务轨道

## 三、任务轨道的详细设计

### 1. 结构：树状 WBS（工作分解结构）

任务轨道不是扁平列表，而是**自顶向下逐层拆解的多层嵌套树**：

```
0000.md（第一层：项目生命周期主阶段，仅5-8项）
  ├── 0010.md（第二层：某阶段的子模块）
  │     ├── 0020.md（第三层：某模块的 原子 任务）
  │     └── 0021.md
  ├── 0011.md
  └── 0012.md
```
备注：上文示例结构仅为任务文件的嵌套关系，非实际目录组织结构，目录组织参照 “七、文件结构总览”

### 2. 拆解原则

- **主路径**：从项目全生命周期出发，先拆出几个大阶段/主项，随项目推进逐步细化到子项，直至原子任务
- **逐步细化拓展**：项目一开始只拆主阶段，随项目推进逐步拆分子项
- **支流汇入**：创意轨道中经评估确认的点子等，作为新任务插入到合适的层级中
- **第一层精简**：第一层只有少量条目（5-8个），每个条目链接到下一层子文件
- **按需加载**：AI 不需要一次性读入整棵树，只读取当前需要操作的层级文件

### 3. 推进方式：主流程线性流水，需要时可建立并行任务集

- 整体呈线性推进：完成第一层第1项 → 第2项 → ...
- 需要时允许少量任务并行执行
- 任何时候都能明确回答："当前进展到哪一步？下一步是什么？"

### 4. 状态收敛：自底向上自动完成

- 每当任务状态变更为完成时，触发状态收敛检查
- 任务文件中所有任务完成后，上一层对应条目自动标记为完成
- 形成"子任务完成 → 父任务完成 → 祖父任务完成 → ...→ 项目完成"的自动收敛链
- **进行中状态向上传播**：每当某任务状态变更为 `>` 且其父任务的引用行当前状态为 `.` 时，自动将父任务同步置为 `>`。该传播自底向上逐层进行，直至根

### 5. 文件结构规范

#### 文件名

- **格式**：纯数字 UID + `.md` 后缀，如 `0012.md`、`0030.md`
- **无类型前缀**：不使用 `T-`、`P-` 等前缀，保持文件名极简
- **全局唯一**：每个文件的 UID 在整个项目系统中唯一，永不重复
- **永不变更**：UID 一旦分配，不因任务内容变更而修改

#### YAML Frontmatter（文件头部元数据）

每个文件必须包含以下 YAML 元数据：

```yaml
---
uid: "0101"
parent_file: "0000"
parent_uid: "0012"
mode: "serial"
title: "战斗系统"
description: "实现攻击、防御、技能释放等核心战斗逻辑"
---
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `uid` | 字符串 | 是 | 当前文件的唯一标识，与文件名一致 |
| `parent_file` | 字符串 | 是（根文件除外） | 父文件 UID：引用本文件那行任务所在的父文件 |
| `parent_uid` | 字符串 | 是（根文件除外） | 引用行 UID：父文件中 `子UID` 指向本文件的那行任务的 UID |
| `mode` | `"serial"` / `"parallel"` | 否（不填表示默认值 `"serial"`） | 当前文件的任务执行模式 |
| `title` | 字符串 | 是 | 任务标题，人类可读（AI自动根据任务生成时的上下文自动生成） |
| `description` | 字符串 | 否 | 任务详细描述，可包含备注、子步骤说明等 |

#### 任务列表表格

文件正文中必须包含一个固定格式的任务列表表格，列顺序和列名严格固定：

```markdown
| UID | SEQ | 标题 | 状态 | 子UID |
|-----|-----|------|------|-------|
| 0020 | 1 | 攻击逻辑 | x | - |
| 0021 | 2 | 防御逻辑 | > | - |
| 0022 | 3 | 技能系统 | . | 0030 |
```

| 列名 | 说明 |
|------|------|
| `UID` | 当前任务的唯一标识，与文件名对应 |
| `SEQ` | 当前文件内的排序序号，纯数字（1、2、3...），仅在当前文件内有效，不外溢到上下层关联和文件名 |
| `标题` | 任务标题，简短描述 |
| `状态` | 任务状态符号（见下文） |
| `子UID` | 子任务文件的 UID；无子任务填 `-`；有子任务填单个 UID（如 `0030`）；**只允许填 1 个 UID** |

### 6. 状态符号规范

采用极简 ASCII 方案，仅定义三种核心状态：

| 状态 | 符号 | 语义 | 输入方式 |
|------|------|------|---------|
| 已完成 | `x` | 任务已完成，叉掉 | 单键 `x` |
| 进行中 | `>` | 任务正在推进中 | 单键 `>` |
| 待开始 | `.` | 任务尚未开始 | 单键 `.` |

**设计理由**：
- 输入极致便捷：三个符号都不需要按 Shift，纯键盘主区单键输入
- 语义直观：`x` = 叉掉完成，`>` = 推进中，`.` = 待办点，符合子弹笔记通用认知
- AI 解析零歧义：纯 ASCII 单字符，不存在 Unicode 多字节问题

### 7. 执行模式规范

#### 串行模式（`mode: "serial"`）

- 任务按 SEQ 顺序依次执行
- AI 推荐"下一步"时，自动定位到第一个状态不为 `x` 的任务
- 子文件默认继承串行模式（可省略声明）
- **串行不强制**：串行模式仅作为 AI 推荐 "下一步" 的默认顺序依据，不禁止乱序推进。用户可按任意顺序标记任务状态（如先完成 SEQ 3 而未完成 SEQ 1），系统不做串行冲突警告，也不整改用户显式设置的状态

#### 并行模式（`mode: "parallel"`）

- 任务无严格先后顺序，可并行推进
- AI 推荐"下一步"时，列出所有状态不为 `x` 的任务，由用户自行选择
- 子文件默认继承串行模式（可省略声明）

#### 模式声明方式

通过 YAML frontmatter 中的 `mode` 字段声明：

```yaml
mode: "serial"   # 串行
mode: "parallel" # 并行
```

#### 嵌套默认规则

- 无论父文件是串行还是并行，子文件的默认模式统一为**串行**
- 如果子文件内部也需要并行，需显式声明 `mode: "parallel"`
- 形成递归嵌套：`默认串行 → 显式声明并行 → 再下一层默认串行 → ...`

### 8. UID 与 SEQ 设计规范

#### 双 ID 架构

| ID 类型 | 作用域 | 用途 | 变更影响 |
|---------|--------|------|---------|
| `UID` | 全局唯一 | 跨文件引用、子文件命名、历史记录 | 永不变更 |
| `SEQ` | 当前文件内 | 当前文件内的任务排序 | 插入任务时仅影响当前文件的 SEQ 列 |

#### UID 全局唯一性
- 所有 UID（包括文件级 UID 和任务级 UID）共用同一个全局编号空间，全局唯一不重复。文件级 UID 用于文件名和 子UID 列引用；任务级 UID 用于标识文件内的具体任务行
- UID 生成采用自增算法，通过记录最大UID，在此基础上自动生成新UID，并更新该记录值
- **UID 不编码层级**：UID 仅是全局自增序号（max+1），与任务在树中的位置、父文件、层级完全无关。文中树状示例中的编号仅用于示意嵌套关系，勿据此推断 UID 层级含义
- **格式化**：UID 采用 4 位数字补零（`0000`、`0001`...`9999`），起自 `0001`；根文件固定为 `0000`。超过 `9999` 后自然进位为 5 位（`10000`），无上限

#### SEQ 局限规则

- SEQ **仅在当前文件内有效**，不携带层级信息
- SEQ **不外溢**到上下层关联、文件名、跨文件引用
- 插入/删除任务时，只需重排当前文件的 SEQ 列，其他文件完全不受影响
- SEQ 使用纯数字（1、2、3...），不使用 `S01`、`P2.3.1` 等复杂格式

#### 跨文件引用

- 所有跨文件引用（如日志、历史记录、AI 定位）统一使用 UID
- 子文件命名直接使用 UID（如 `0030.md`），不包含描述性文字
- 人类通过 YAML 中的 `title` 和 `description` 获取可读信息

### 9. 子文件管理规范

#### 子UID 约束

- 每个任务只允许有一个子文件，`子UID` 列**只允许填 1 个 UID**
- 不允许在 `子UID` 列中用逗号分隔多个 UID
- 一个任务有多个子任务的需求，通过在子文件中填入多条任务来实现（可串行，也可并行）

#### 子文件命名

- 文件名 = UID + `.md`，如 `0030.md`
- 不包含任何描述性文字，保持极简
- 人类通过 YAML 中的 `title` 识别文件内容

#### 父引用回溯

每个子文件必须在 YAML 中声明 `parent_file` 与 `parent_uid` 两个字段，二者共同构成定位链路：

- `parent_file`：父文件 UID，即引用本文件那行任务所在的文件（本文件在目录树中的所属层级依据此判定）
- `parent_uid`：引用行 UID，即父文件中 `子UID` 列指向本文件的那行任务的 UID
- 使用 `parent_file` 定位到父文件，再用 `parent_uid` 定位到父文件中的具体引用行
- 根文件（如 `0000.md`）不需要这两个字段

### 10. 删除与移动规范

#### 删除

- **叶子任务行**：可直接删除，随后仅需重排当前文件的 SEQ 列（保持连续）
- **带子文件的任务行**（`子UID` 不为 `-`）：禁止直接删除。必须先处理其子任务（通常先逐一完成后再删，或经用户确认后递归删除其子文件），递归删除时逐层向用户确认
- **UID 永不复用**：删除后该 UID 留空，不分配给后续新任务；同时更新 `.flow/demand-pipeline.md` 中的最大 UID 记录（若删除的是最大值则保持原值，不回落）

#### 移动

- 允许将任务移动到其他父文件下（跨父移动），需同步维护 4 处：
  1. 原父文件表中删除该行的 `子UID` 引用，并重排原文件 SEQ
  2. 目标父文件中新增一行并记录 `子UID`，分配新的文件内 SEQ
  3. 子文件 YAML 更新 `parent_file` 与 `parent_uid`；层级变化时同步移动到对应 layerN 目录
  4. 更新 `.flow/demand-pipeline.md` 摘要
- 移动不改变 UID（全局唯一，永不变更）

## 四、创意轨道的详细设计

- 用户随时提出的新点子，统一存入创意轨道
- 不直接进入执行计划，暂存待处理
- 经 用户评估确认后，升格为任务轨道中的新条目，插入对应层级, 并直接从创意轨道表格中删除该行（不保留历史记录，删除后原 `序号` 留空）
- 录入创意： AI 在表格末尾追加一行，自动分配 `序号`（当前最大序号 +1），日期为当前日期，标签根据创意内容自动生成初步分类

### 列结构与自增序号

创意轨道表格固定 5 列：

| 列名 | 说明 |
|------|------|
| `序号` | 自增数字，仅用于精确定位条目（更新/删除/升格都按此定位）。删除/升格后该序号留空不补位，后续新条目仍取当前最大值 +1 |
| `日期` | 条目录入日期（YYYY-MM-DD），AI 录入时自动填写当天 |
| `标题` | 创意标题 |
| `描述` | 创意描述 |
| `标签` | AI 根据内容自动生成的初步分类，逗号分隔 |

### 内容示例

```markdown
---
title: "创意轨道"
description: "暂存待评估的点子池，经评估后升格为任务轨道条目"
---

| 序号 | 日期 | 标题 | 描述 | 标签 |
|------|------|------|------|------|
| 1 | 2026-09-20 | 动态天气系统 | 玩家探索时天气随时间变化，影响视野和NPC行为 | 玩法,环境 |
| 3 | 2026-09-21 | 角色皮肤商城 | 用户可购买外观皮肤，不影响数值 | 经济,UI |
```

## 五、实现方式：Skill为主，rules辅助

任务轨道和创意轨道都做成 **Skill**（而非 Subagent），原因：
- IDE 模式下 Chat 可以随时通过斜杠命令或自然语言触发
- 轻量级，不需要独立上下文窗口
- 符合"Skill 管规则/操作"的定位

**Skill 结构（方案 A）+ 共享规则文件**：

- **3 个操作型 Skill**（用户可直接 slash 或自然语言触发）：
  - `flow-task`（任务轨道）：创建/更新/状态变更/删除与移动
  - `flow-idea`（创意轨道）：添加/更新/升格
  - `flow`（会话与概览）：初始化 / 会话恢复(`/flow-resume`) / 概览
- **1 份共享规则文件 `flow-core`**（非操作型，仅供 flow-task/flow-idea 在创建与维护任务时加载）：
  - 集中定义全部**共享不变量**：UID 生成（读最大 UID → max+1 → 4 位补零 → 覆盖记录）、SEQ 重排、状态收敛、layerN 目录判定、文件格式校验
  - `flow-task` 创建任务/子文件、`flow-idea` 升格创建任务时，都**先加载 `flow-core` 再执行**，实现"规则只有一处定义"，避免跨 skill 复写漂移

**Skill 落点与单一真相源**：
- 上述 Skill 与 `flow-core` 规则文件均存放于**项目内**，随项目一起版本化
- **单一真相源**：所有工作流规则只写入 Skill 与 `flow-core`；`.flow/README.md`、`.flow/STRUCTURE.md`、`demand-pipeline.md` 等元信息文件不做规则复述，只做一句话概述 + 链接
- 与执行管线（CCGS、GameDesignOS、GDD）**不做引用格式的强制约定**，任务 description 可自由引用

### 手动触发形式

用户通过以下方式主动触发操作：

- **斜杠命令**：如 `/flow-task-create`、`/flow-task-update`、`/flow-idea-add` 等，提供结构化的操作入口
- **自然语言**：如"帮我创建一个任务：实现登录功能"、"把创意'动态天气'升格为任务"等，由 AI 解析意图后执行

手动触发覆盖的操作场景：

| 轨道 | 操作类型 | 说明 |
|------|----------|------|
| 任务轨道 | 创建任务 | 在指定层级插入新任务，自动生成 UID 和 SEQ |
| 任务轨道 | 更新任务 | 修改任务标题、描述、状态等属性 |
| 任务轨道 | 状态变更 | 将任务状态标记为 x/>/.，触发状态收敛检查 |
| 任务轨道 | 会话恢复 | 新会话时经 `/flow-resume` 触发，扫描任务树定位当前进展位置和下一步建议（非自动） |
| 创意轨道 | 创建创意 | 在创意轨道表格中追加新创意条目 |
| 创意轨道 | 更新创意 | 修改已有创意的标题、描述、标签 |
| 创意轨道 | 创意升格 | 将创意转化为任务轨道中的新条目，并从创意轨道中移除 |

### 自动维护形式

AI 在业务执行过程中，能够判定当前执行任务的完成，进而触发任务列表中任务条目的状态变更，并自动执行以下维护动作，确保任务轨道的一致性和完整性：

- **自动更新任务状态**：AI 根据执行结果判定任务完成后，自动将对应任务的状态更新为已完成（`x`），无需用户手动标记。并触发后续的状态变更与维护流程
- **状态收敛**：当某任务的所有子任务均标记为完成（`x`）时，自动将该任务的父级状态更新为完成，形成自底向上的级联完成链
- **UID 生成与维护**：每次创建新任务时，自动读取当前最大 UID 值并递增生成新 UID，写入 YAML frontmatter 和文件名，确保全局唯一性
- **SEQ 变更维护**：插入/删除任务时，自动重新编排当前文件内的 SEQ 列，保证序号连续且不受其他文件影响

自动维护的执行时机：

| 触发事件 | 自动执行动作 |
|----------|-------------|
| 创建新任务 | 生成 UID、分配 SEQ、写入父级引用、更新需求管道摘要 |
| AI判定任务完成 | AI判定任务完成并更新状态为已完成、触发状态收敛、更新进度摘要 |
| 创意升格为任务 | 在任务轨道中创建新条目、分配 UID/SEQ、从创意轨道删除原行 |
| 删除/移动任务 | 按"三.10 删除与移动规范"执行：更新父级子UID引用、重排 SEQ、同步更新需求管道摘要 |

### 两种形式的协作关系

手动触发是"用户驱动"的操作入口，自动维护是"系统驱动"的后台保障。自动维护由 AI 判定任务完成所驱动，两者协同工作：

1. AI 判定当前任务执行完成
2. 系统执行核心操作（更新任务状态）
3. 系统自动维护一致性（状态收敛、UID/SEQ 检查、摘要更新）
4. AI 生成会话摘要，建议下一步行动

这种设计确保了：

- **用户可控**：用户手动操作均可控可追溯；AI 自动判定的变更同样经过系统校验，避免系统自动改动导致不可预测的结果
- **数据一致**：自动维护保证任务树的完整性，无需用户手动维护关联关系
- **低学习成本**：用户只需关注"做什么"，"怎么做"和"一致性维护"由系统自动处理

## 八、AI 行为规范

### 1. 初始化

- AI 首次接触项目时，从根文件（`0000.md`）开始扫描
- 读取 YAML 元数据获取 `mode`、`title`、`description`
- 解析任务列表表格，构建任务树
- **自动定位当前进展位置**：根据各任务状态，自动找到项目当前所在的节点，无需用户手动选择

### 2. 组织方式：递归下钻 + 串行/并行模式

这是 AI 理解和管理任务轨道的两种组织方式：

#### 递归下钻

- AI 从根文件出发，逐层向下扫描任务树
- 任务的 `子UID` 列，若不为 `-`，代表有子任务，自动打开对应子文件继续扫描，完成对任务的逐层查找
- 通过 `parent_file` / `parent_uid` 支持上下文回溯，形成完整的任务链路
- 递归下钻的目的是服务于**自动发现**项目当前进展到哪个层级、哪个任务

#### 串行模式（`mode: "serial"`）

- 任务按 SEQ 顺序依次执行

#### 并行模式（`mode: "parallel"`）

- 同任务文件中，所有任务无严格先后顺序，可并行推进

---

### 3. 自动发现当前进展位置

需要时 AI 自动执行以下流程，以发现当前项目进展状态：

1. **从根文件出发**：读取 `0000.md`，扫描任务列表
2. **逐层下钻**：
   - 按 SEQ 顺序扫描，跳过状态为 `x` 的任务，找到第一个状态不为 `x` 的任务
   - 若该任务有 `子UID`，自动打开子文件继续扫描
   - 重复此过程，直到找到没有 `子UID` 的任务节点（即最末梢节点）
3. **输出当前进展**：向用户报告"当前进展到 [层级路径] 的 [任务标题]"

### 4. 下一步推荐

基于自动发现的当前进展位置，AI 给出下一步建议：

- 到达末梢节点后，读取该文件的 mode 字段：
  - 若为 serial（或默认）→ 串行模式行为
  - 若为 parallel → 并行模式行为
- **串行模式**：当前末梢节点即为下一步，直接推荐执行该任务
- **并行模式**：当前末梢节点所在的任务文件中，列出所有状态不为 `x` 的任务，由用户选择优先推进哪一个
- **已完成所有任务**：若当前层级所有任务状态均为 `x`，自动向上回溯到父层级（依据 `parent_file` / `parent_uid`），继续按 SEQ 顺序找下一个非 `x` 任务，重复下钻流程

### 5. 状态更新

- 用户完成任务后，AI 协助更新对应任务的状态符号
- 更新时只需修改当前文件的表格行，不影响其他文件

### 6. 会话摘要

每次状态更新后，AI 自动生成简短摘要：

- 本次会话完成了哪些任务
- 当前项目整体进展位置
- 下次会话建议从哪个任务开始
- 提醒用户切换为新会话，减少新任务的上下文长度
- 会话恢复**不自动触发**：新会话开场 AI 不做主动扫描；用户通过 `/flow-resume` 明确指示时，AI 才执行会话恢复流程
- 若本次有 AI 自动判定的状态变更，随摘要列出变更清单，供用户复核/回滚；删除类高风险动作在摘要中再次提示

## 十一、设计原则总结

| 原则 | 体现 |
|------|------|
| **人类友好** | 文件名极简、YAML 元数据可读、状态符号直观 |
| **AI 易解析** | 固定列格式、纯 ASCII 状态符号、结构化 YAML |
| **维护成本低** | SEQ 仅限文件内、UID 永不变更、子UID 只允许 1 个 |
| **递归可扩展** | 双 ID 架构、父子 UID 回溯、模式嵌套默认规则 |
| **零歧义** | 固定 5 列表格、明确的模式声明、严格的子UID 约束 |
